# PR 리뷰 에이전트 동작 명세서

**문서 성격**: 이 문서는 "왜 도입해야 하는가"를 설득하는 제안서가 아니라, **에이전트가 PR을 받았을 때 내부적으로 어떤 판단을 어떤 순서로 내리는지**를 서술하는 동작 명세서입니다. 구현 착수 전 로직 검증용으로 작성했습니다.

**검토 기준 충족 매핑**

| 검토 기준 | 이 문서에서 해당하는 부분 |
|---|---|
| 문제 분해 (도메인 문제를 하위 문제로 나눔) | 2절 입출력 정의, 3.2절 (컨벤션/디자인시스템/정적오류/커뮤니케이션 4개 항목으로 분리) |
| 절차 표현 (순서 있는 단계로 서술) | 3절 처리 파이프라인 (3.1 → 3.5 순서), 4절 의사결정 흐름 요약 |
| 패턴·추상화 (반복 구조 정리 + 핵심만 추출) | 3.3절 PR 목적 분류 조건 분기 (반복되는 PR 패턴을 3가지 유형으로 추상화), 3.4절 "확신 없으면 사람에게" 단일 원칙으로 판단 로직 축약 |

---

## 1. 개요

| 항목 | 내용 |
|---|---|
| 에이전트 역할 | PR 생성/업데이트 시점에 정형화된 검토 항목을 선처리하고, 사람이 봐야 할 항목만 추려서 리포트 형태로 전달 |
| 처리 범위 | 컨벤션 준수, 디자인 시스템 준수, 정적 오류, PR 내 미해결 커뮤니케이션 항목 |
| 처리 제외 범위 | 비즈니스 로직 타당성, 아키텍처/구조 판단, 엣지케이스 최종 승인 |
| 동작 원칙 | 규칙 기반(rule-based) 판단만 수행. 애매하면 "판단 보류 → 사람에게 전달"이 기본값 |

---

## 2. 입출력 정의

**입력**
- PR diff (변경 파일, 변경 라인)
- PR 메타데이터 (제목, 라벨, 작성자, 파일 수, 변경 라인 수)
- 내부 컨벤션 규칙셋 (기능 단위로 분리된 데이터)
- 디자인 시스템 규칙셋 (토큰/컴포넌트 whitelist)
- CI 결과 (Lint, Type-check, Build Pass/Fail)

**출력**
- 구조화된 리뷰 리포트 1건 (PR 코멘트로 게시)
  - 자동 처리 요약 (통과/위반 카운트)
  - 사람 검토 필요 항목 리스트 (우선순위 포함)
  - PR 목적 분류 태그

---

## 3. 처리 파이프라인

### 3.1 PR 감지 및 메타데이터 추출
PR 생성 또는 업데이트 이벤트 수신 시, 에이전트는 diff, 변경 파일 목록, PR 제목, 라벨, 변경 라인 수를 추출한다. 이 단계는 순수 데이터 수집이며 판단은 없다.

### 3.2 자동화 검토 (Rule-based Checks)

**3.2.1 내부 컨벤션 검토**
- 판단 기준: 기능 단위로 사전 정의된 컨벤션 규칙셋 ↔ 변경 코드 패턴 매칭
- 출력: 위반 항목 (파일:라인, 규칙 ID, 심각도)
- 비고: 규칙셋이 코드로 존재해야 함. "팀 노션 페이지에 적힌 컨벤션"은 매칭 대상이 될 수 없음

**3.2.2 디자인 시스템 컨벤션 검토**
- 판단 기준: 디자인 토큰/승인된 컴포넌트 목록 ↔ 변경 코드 내 스타일·컴포넌트 사용 비교
- 출력: 위반 항목 (하드코딩된 색상값, 미승인 컴포넌트 직접 사용 등)
- 비고: 규칙셋 소스가 정의돼야 판단 가능 (Figma 토큰 export든 별도 스키마든)

**3.2.3 시맨틱 에러 감지**
- 판단 기준: CI에서 이미 수행된 정적 분석(ESLint, TypeScript) 결과를 수집 → severity 재분류만 수행
- 출력: Pass/Fail + 에러 상세
- 비고: 에이전트가 새로 분석하지 않고, 기존 도구 결과를 "읽고 요약"하는 역할

**3.2.4 PR 내 커뮤니케이션 항목 감지**
- 판단 기준: PR 본문·커밋 메시지 내 미해결 마커(`TODO`, `FIXME`, 물음표로 끝나는 문장 등) 패턴 매칭
- 출력: 주석/문의 하이라이트 리스트 (해결 여부 미확인 상태로 표시)

### 3.3 PR 목적 분류 (패턴 감지)

입력: PR 제목 키워드, 변경 파일 수, 변경 라인 수, 라벨

판단 로직 (조건 분기, 임계값은 예시):

```
IF 제목/라벨에 "fix", "bug" 포함 AND 변경 파일 수 < N
  → 분류: 오류 수정 → 검토 강도: 재현/회귀 여부 중심
ELSE IF 신규 파일 다수 AND 변경 라인 수 > M
  → 분류: 기능 추가 → 검토 강도: 전체 항목 검토
ELSE IF 변경 파일 수 낮음 AND 변경 라인 수 매우 작음
  → 분류: 단순 수정 → 검토 강도: 자동 검토 결과로 갈음, 사람 확인은 최종 승인만
ELSE
  → 분류 보류 → 사람이 직접 분류
```

N, M 값은 실 데이터 기반으로 정해야 함. 지금은 자리표시자.

### 3.4 사람 검토 필요 항목 판별

판단 기준:
- 3.2에서 규칙셋 부재/애매성으로 자동 판단하지 못한 항목
- 3.3에서 분류상 사람 개입이 필요하다고 태깅된 항목 (기능 추가, 분류 보류)

이 단계의 핵심 원칙: **에이전트가 확신 없는 항목은 전부 사람에게 넘긴다.** 애매한데 자동 승인 처리하면, 이 에이전트는 "빨리 도와주는 도구"가 아니라 "몰래 구멍 내는 도구"가 됩니다.

### 3.5 리포트 생성 및 게시

구성:
1. 자동 처리 요약 (컨벤션/디자인시스템/정적분석 통과·위반 카운트)
2. 사람 검토 필요 항목 리스트 (우선순위: 분류 보류 > 기능 추가 관련 > 그 외)
3. PR 목적 분류 태그
4. 관련 컨텍스트 (연결된 이슈, 미해결 커뮤니케이션 항목)

출력 형식: 마크다운 코멘트, PR에 자동 게시

## 4. 의사결정 흐름 요약

```
PR 이벤트 수신
   ↓
메타데이터 추출
   ↓
[자동화 검토] 컨벤션 → 디자인시스템 → 정적분석 → 커뮤니케이션 항목
   ↓
PR 목적 분류 (조건 분기)
   ↓
사람 검토 필요 항목 취합 (자동판단 실패 + 분류상 필요 항목)
   ↓
리포트 생성 → PR 게시
```

## 5. 구현 전 정의해야 하는 미확정 값

명세는 여기까지 로직으로 정리했지만, 아래는 숫자나 소스가 정해지지 않으면 실제로는 못 돌아가는 부분입니다.

1. **임계값 N, M**: PR 분류에 쓰는 파일 수/라인 수 기준값 — 실제 팀 PR 데이터 샘플링해서 정해야 함
2. **디자인 시스템 규칙셋 소스**: Figma API 연동인지, 별도 JSON 스키마 관리인지 결정 필요
3. **컨벤션 규칙셋 관리 방식**: 코드 내 lint config로 관리할지, 별도 규칙 엔진을 둘지
4. **판단 보류(Else) 케이스 처리**: 지금은 "사람에게 넘긴다"까지만 정의됨. 얼마나 자주 발생하는지 실측 필요 (너무 자주 보류하면 이 에이전트는 그냥 알람 봇이 됩니다)
5. **False Positive 피드백 루프**: 사람이 "이건 오탐"이라고 표시했을 때 다음 판단에 반영되는 메커니즘 미정

이 5개는 로직의 문제가 아니라 **데이터/정책의 문제**라서, 다음 단계에서는 실제 PR 로그 샘플을 가지고 임계값부터 채워보는 걸 추천합니다.
